# Releasing a New Version

Run commands from the repository root. Read `docs/releases.md` and
`.github/workflows/release.yml` before acting; they define the current packaging
and publication behavior. Both Cargo packages are private (`publish = false`);
releases distribute native archives through GitHub, not crates.io or WASM.

## Prepare the version

1. Inspect the working tree, branch, remotes, recent commits, and existing local
   and remote tags/releases. Identify the intended release commit and target
   repository; preserve unrelated work.
2. Use the version requested by the user. If none was supplied and repository
   context does not establish one, ask for it while continuing independent
   inspection. Keep the two package versions and the `v<version>` tag aligned.
   Hyphenated tags are published as prereleases by this workflow.
3. Update `[package].version` in both `Cargo.toml` and `native/Cargo.toml`.
   Refresh the workspace package entries in `Cargo.lock`, for example with
   `cargo check --workspace --offline` after editing the manifests. Inspect the
   lockfile diff and preserve unrelated dependency versions; do not run a broad
   dependency upgrade as part of a release.
4. Review changes since the previous release for user-facing documentation needs.
   GitHub release notes are generated by the workflow; prepare custom notes only
   when requested or needed to explain the release.
5. Run `bash tools/verify_native.sh` against the final source. Consult
   `README.md` and the script for prerequisites. All checks must pass before
   tagging; report missing prerequisites or failures instead of treating partial
   verification as release readiness. Review the resulting diff and version
   alignment before committing.

## Tag and publish

Respect the user's requested scope: preparation ends with a reviewable local
change. An explicit request to publish/release authorizes the corresponding
commit, push, and tag operations; do not ask again when already authorized. If
publication is outside the request, finish preparation before seeking any needed
authorization. Pushing a `v*` tag triggers automatic publication after checks;
the workflow's draft phase is not a manual approval gate.

For an authorized release, commit the reviewed release changes and push the
source to the intended remote branch before tagging. Confirm the source commit
is available on that remote, the version tag is unused locally and remotely,
and the working tree contains no uncommitted release changes. Create the tag at
that exact commit and push only that tag. Do not force-push or move a published
tag. If the requested tag already exists, inspect its commit and release state
and resolve the conflict before making a mutation.

## Verify publication

Follow the tag's `Release native` workflow run using GitHub tooling, such as
`gh run list`, `gh run view`, and `gh run watch`. Confirm its commit matches the
intended release. The workflow tests, lints, and builds on matching runners for
Linux x64, Windows x64, macOS Intel x64, and macOS Apple Silicon ARM64. Local
verification does not replace those platform checks.

Verify the published release has the correct tag and prerelease status and all
eight expected assets: four archives and their matching `.sha256` files. Use
the archive names in `docs/releases.md`. Download them into a temporary or
`target/` directory, verify the checksums, and inspect archive listings for the
native executable, README, config, docs, and examples. The GitHub workflow creates
a draft, uploads assets, then publishes it automatically.

On failure, inspect the failed job and current release/assets before retrying.
Reruns replace matching assets and are not atomic for an already published
release. Do not repeatedly rerun publication without understanding the failure;
fix source problems in a new commit/version rather than moving a published tag.
Report the version, commit, verification results, workflow and release links,
and any remaining blocker. Claim publication only after checking its final state.
